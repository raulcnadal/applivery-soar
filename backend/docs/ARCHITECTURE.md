# Architecture Guide

This is the developer-facing companion to [README.md](README.md) (project overview + deployment) and the [docs/](docs/) admin guides (what each screen does for an end user). This document explains how the codebase itself is put together — for an engineer picking up the project for the first time.

The app is a Vue 3 + TypeScript single-page frontend (`frontend/`) and a Node.js/Express + TypeScript backend (`backend/`), backed by Postgres via Prisma ORM. Every account is an existing Applivery Collaborator — there's no local user database. Every device/policy/app action ultimately calls Applivery's own management API on the caller's behalf, using their own forwarded Applivery session token.

## 1. Frontend (`frontend/`)

Vue 3 with `<script setup>` and the Composition API throughout, built with Vite. State lives in Pinia stores (one per feature area, `frontend/src/stores/*.ts` — 25 in total, e.g. `devices.ts`, `compliance.ts`, `workflows.ts`, `auth.ts`, `roles.ts`, `catalogs.ts`, `geofencing.ts`), routed with Vue Router 4 (`createWebHistory`, so any deployment serving this SPA needs a fallback-to-`index.html` rule for non-file paths — see §7).

UI primitives come from `@applivery/bluesky-vue`, a component library vendored at `packages/bluesky-vue` and consumed via a relative path alias in `frontend/vite.config.ts` (not published to a registry — its own `node_modules` need installing separately, see the Dockerfiles). Feature-specific visualizations that aren't part of that library are hand-wrapped directly: `globe.gl` for the Playground 3D device globe, `vue-echarts`/ECharts for Overview/Reporting charts, `grid-layout-plus` for the draggable widget grid, and Leaflet (+ `leaflet.markercluster`) for the Devices map — there's no maintained Vue binding for Leaflet, so it's wrapped directly in a thin component, same pattern as the globe widget.

Top-level views (`frontend/src/views/`): `OverviewView`, `PlaygroundView`, `DevicesView`, `ComplianceView`, `WorkflowsView`, `CasesView`, `ReportingView`, `AuditLogsView`, `SettingsView`, `LoginView`. Settings alone hosts 20 sub-sections as tabs inside one view (see `docs/settings.md` for the full list) rather than 20 separate routes.

The API client (`frontend/src/api/http.ts`) is a single Axios instance with a request interceptor that stamps three things onto every call automatically, so no component ever attaches them by hand: the dashboard JWT (`X-Dashboard-Token`), the active workspace slug (`X-Workspace-Slug`), and the user's live Applivery bearer token (`Authorization`). `GET`/`POST /api/state` and `/api/layout` are the one deliberate exception — they always pin `X-Workspace-Slug: global`, since that pair of endpoints is shared dashboard-wide state, not per-workspace.

## 2. Backend (`backend/`)

Express + TypeScript, organized as one module per feature area under `backend/src/modules/` (19 modules: `auth`, `devices`, `compliance`, `catalogs`, `workflows`, `cases`, `integrations`, `threatIntel`, `config`, `settings`, `roles`, `auditLogs`, `analytics`, `reports`, `appLists`, `systemHealth`, `health`, `help`, `geofencing`). Each module is typically `*.controller.ts` (routes + request/response shaping), `*.service.ts` (business logic, the actual Applivery/Prisma calls), and `*.schemas.ts` (Zod request validation). Routes are wrapped in a shared `asyncHandler` so a thrown/rejected error always reaches the centralized error-handling middleware rather than needing a try/catch in every handler.

`geofencing` (draw a zone on the Playground map, reference it from a Compliance Policy condition — see `docs/geofencing.md`) is the one module with no equivalent in the original app at all — a disclosed net-new capability built on top of the device location data already gathered via Applivery's API, reusing the `compliance` RBAC area rather than introducing its own.

Around 185 routes total (confirmed by `authRequired.test.ts`, which walks the live Express router stack rather than trusting a static count — see §8). Every route requires the dashboard token except a small, explicit allowlist of externally-triggered receivers (device self-report webhooks, the Applivery inbound webhook, trigger-fire URLs, and the two scheduler-poke endpoints gated by a separate `TRIGGER_SECRET` instead).

## 3. Storage layer — Postgres via Prisma

One `schema.prisma` (64 models) is the single source of truth for every persisted store — Compliance Policies, Workflows (with version history), Triggers, Roles, Cases, Integrations, Threat Intel providers, the five global intelligence catalogs, Automation Credentials, System Health heartbeats, GeofenceZone/DeviceLocation (geofencing's zone assets and per-device position cache), and so on. Every workspace's data lives in the same Postgres database, scoped by a `workspaceSlug` column on each table — one database to back up, one place migrations apply, and the only architecture that supports the durable-workflow `wait` step cleanly across restarts.

Migrations are Prisma's own (`prisma migrate deploy`, run automatically at container start — see the backend `Dockerfile`'s `CMD`). Postgres is required for this build to start at all.

## 4. Authentication & RBAC

Login is a thin proxy to Applivery's own traditional-credentials login API (`POST /api/auth/login`) — there's no separate signup or local password. A successful login returns two independent things the frontend holds onto: this app's own dashboard JWT (30-day expiry, the sole gate on every `/api/*` route, verified by `middleware/auth.middleware.ts`), and the user's real Applivery session (access/refresh token pair + expiry, much shorter-lived, forwarded as `Authorization: Bearer <token>` on every subsequent call to this app's backend, which in turn forwards it straight to Applivery's own API).

Two frontend-only mechanisms keep that Applivery session alive for as long as someone's actually using the app, independent of the dashboard JWT (`composables/useSessionGuards.ts`, mounted from `AppShell.vue`): a proactive refresh loop polls every 60s and renews the Applivery token (`POST /api/auth/refresh`) whenever it's within 60s of expiring, and `api/http.ts`'s response interceptor additionally retries once-after-refresh on a 401 that specifically indicates the forwarded Applivery token went stale (a fallback for whatever the polling loop's 60s window ever misses, e.g. a backgrounded tab's throttled timers). Layered on top, a separate idle-timeout watcher in the same composable resets a plain timer on any mouse/keyboard/scroll activity and signs the user out if it ever actually fires — the real enforcement of the configurable **Settings → General → Idle Session Timeout** (30min–8h, default 60min; `docs/settings.md#general`). Genuine inactivity past that threshold is the only thing that should ever end an active session.

RBAC (`middleware/rbac.middleware.ts`) is this app's own layer entirely — Applivery's Collaborator role is a fixed 5-value enum (Owner/Admin/Editor/Viewer/Unassigned) with no fine-grained permission model of its own. Precedence, in order: (1) Applivery Collaborator role `owner` → Super Admin, unconditional full access, the only automatic bypass; (2) everyone else is resolved by matching a "role tag" read off their Applivery Collaborator record against the tag values a SOAR Role (`Settings → Roles`, Super-Admin-only) has been configured to accept; (3) no confirmed match → denied outright, never a default-read-only fallback. Resolution happens at login and at every workspace switch (`POST /api/auth/resolve-access`) and is cached server-side, in-memory, 12h TTL, fail-closed (a caller who hasn't resolved access for the current workspace this session is denied rather than re-resolved live inline).

Eight feature areas (`devices`, `compliance`, `workflows`, `cases`, `integrations`, `reporting`, `settings`, `auditLog`), each with three access levels (`none`/`read`/`manage`), gated per-route via `requirePermission({area, level})`. Five additional "risky action" checkboxes (`canDeletePolicyOrWorkflow`, `canRunDestructiveWorkflow`, `canEditIntegrationSecrets`, `canExportOrImportConfig`, `canBulkTriage`) are orthogonal to the area/level grid and gate specific destructive endpoints regardless of a role's general access level.

## 5. Background jobs

25 recurring jobs (`jobs/backgroundJobs.ts` is the single registry, `backgroundJobs.test.ts` asserts the exact count and every expected `jobKey` so a loop can never get silently wired in or dropped) cover everything that needs to run with no human signed in: the six global intelligence-catalog refreshers (OS Update/MSRC, Vulnerability/EUVD, OS Lifecycle, Apple GDMF, Apple device identifiers, MITRE ATT&CK), the Compliance scheduler, the durable-workflow wait-step resumer, the script-run log reconciler, ticket-status sync, Case SLA monitoring, audit-log rotation, the batch log-export scheduler, the System Health alert monitor, the per-workspace Vulnerability Service refresher and its threat-intel counterparts (MISP, VulnCheck, binary-integrity, OSV.dev Android, SOFA Apple), the analytics snapshot capture, the scheduled-report sender, the installed-apps rolling refresher, geofencing's device-location refresher (budgeted, oldest-synced-first, scoped only to devices an enabled Compliance Policy's geofence condition actually cares about — see `docs/geofencing.md`), and the Event Notify metrics rotation job. Every job records a heartbeat (`services/systemHealth.ts`) at the end of each run, success or failure, surfaced in `Settings → System Health`.

By default every job runs as a plain `setInterval` loop in the same Node process, staggered 15s apart at boot so they don't all fire in the same instant. If `REDIS_URL` is configured, the same 25 jobs instead run as BullMQ repeatable jobs against Redis (`queue/backgroundQueue.ts`) — this matters only once the backend is scaled to more than one replica, since N independent `setInterval` loops across N replicas would each fire independently (double/triple/N-tuple-firing the compliance evaluator, workflow resumer, etc.); BullMQ's Redis-lock-based job distribution instead guarantees exactly one instance of each job runs cluster-wide, regardless of replica count.

Automation Credentials (`Settings → Workspace Automation`, `modules/settings/automationCredential.service.ts`) are what let these jobs call Applivery's API unattended, per workspace — the app has no admin who's "always logged in," so a real signed-in session's tokens are captured on demand and self-refreshed thereafter.

## 6. Outbound Applivery API client & rate limiting

`services/appliveryClient.ts` wraps Axios in a singleton that never throws on a non-2xx response (callers inspect `.status` themselves) and auto-retries on `429` using the `Retry-After` header. Every outbound call is gated by a shared `TokenBucket` (`utils/tokenBucket.ts`) tuned to Applivery's own documented ceiling — 10,000 requests/hour with burst capability (`docs.applivery.com`) — configurable via `APPLIVERY_RATE_LIMIT_PER_HOUR`/`APPLIVERY_RATE_LIMIT_BURST` in case a given org's actual contract grants a different limit. List-endpoint pagination (`services/appliveryPaginate.ts`) walks every page using Applivery's own documented maximum page size (10,000) rather than a smaller default, and logs loudly — rather than silently truncating — if a fleet is ever larger than the configured safety ceiling.

Inbound, three tiers of per-IP rate limiting (`middleware/rateLimiter.middleware.ts`) protect this app's own API: a tight limit on `/api/auth/login`, a looser one on the two secret-in-URL-path receivers, and a default catch-all for everything else.

## 7. Deployment topology

`docker-publish.yml` publishes two multi-arch images to GitHub Container Registry (ghcr.io), attached to this repo, on every push to `main`: `ghcr.io/raulcnadal/applivery-soar` (backend/Dockerfile) and `ghcr.io/raulcnadal/applivery-soar-frontend` (frontend/Dockerfile), using the workflow's own `GITHUB_TOKEN` — no external registry credentials to manage. Both packages are set to public visibility — a one-time manual setting on GitHub, since GHCR decouples package visibility from repo visibility and `GITHUB_TOKEN` can't change it from within the workflow — so this repo stays private while a deployment host pulls both images anonymously, no `docker login` needed. Two supported deployment shapes both pull from these, no local build required:

- **Split services (current default, `docker-compose.yml`)** — `soar-frontend` (`ghcr.io/raulcnadal/applivery-soar-frontend`, Nginx serving the built Vue SPA, reverse-proxying `/api/*` to the backend so the browser only ever talks to one origin — no CORS needed), `soar-backend` (`ghcr.io/raulcnadal/applivery-soar`, API-only), `soar-db` (Postgres), and `soar-redis` (optional — only needed if `soar-backend` is scaled to more than one replica, see §5).
- **Single container** — `ghcr.io/raulcnadal/applivery-soar` alone also bundles the frontend (`COPY --from=frontend-builder ... /app/frontend/dist`) and Express falls back to serving it as static files for any non-`/api` route (`app.ts`) if no separate frontend service is fronting it. Same image either way — it's just unused static files when `soar-frontend`'s Nginx is what's actually serving traffic.

Building from local source instead of pulling (e.g. to test unreleased changes) is a `docker-compose.build.yml` override layered on top of `docker-compose.yml`.

Either way, the backend refuses to start without `DASHBOARD_SECRET` and `DATABASE_URL` set.

## 8. Testing

Backend: Vitest + Supertest (`backend/src/test/`), run against a fully in-memory mocked Prisma client, a mocked `appliveryClient`/raw `axios` (so catalog refreshers don't make real outbound calls during tests), and the app's real Express router (`app.ts`'s `createApp()`), so route/RBAC/rate-limit assertions exercise actual middleware rather than a stub. CI (`ci.yml`) additionally runs `prisma generate` + `prisma migrate deploy` against a real ephemeral Postgres service, and runs the full suite there too — the one thing that can't be validated in a sandboxed environment without a real database. Frontend: Vitest for unit tests, `vue-tsc -b && vite build` as the authoritative typecheck.

## 9. Native agents & self-reported device data

Three companion repos — [`applivery-soar-agent-windows`](https://github.com/raulcnadal/applivery-soar-agent-windows) and [`applivery-soar-agent-macos`](https://github.com/raulcnadal/applivery-soar-agent-macos) (native Go), plus [`applivery-soar-agent-mobile`](https://github.com/raulcnadal/applivery-soar-agent-mobile) (Flutter, iOS + Android), all private, no shared code with this repo — are small agents that run on managed endpoints and push data this app has no other way to collect, since Applivery's own MDM API doesn't expose it. All three report through the same device-facing endpoints in `modules/devices/deviceData.controller.ts`, matched by serial number the same way regardless of platform — mobile gets its real hardware serial via Applivery's `{{device.serialNumber}}` Managed App Configuration interpolation tag (Apple/Android both block a third-party app from reading its own serial directly), so no code change was needed here to support it. `POST /api/device-data/report` (device-report-secret **or** mTLS client-cert gated per workspace, see `backend/docs/mtls-agent-auth-roadmap.md`) carries a fixed set of attributes (BitLocker/FileVault, firewall, OS build, and platform-specific security posture) plus, since the Custom Device Checks feature (§9.1), an arbitrary `customCheckResults` map (Windows/macOS only, see below); `POST /api/device-data/report-apps` carries installed-application inventory. Reported data is stored per-device (`DevicePushData`) and surfaces as **Self-Reported Attribute** and **App List** conditions in Compliance Policies (`docs/compliance.md`).

The mobile agent now fully reports through this same contract as of its 5-phase device-telemetry roadmap (see that repo's `ARCHITECTURE.md` §2.8-§2.13 for the full build history):

- **iOS**: `devicePasscodeSet` (a Keychain-accessibility probe — also the only signal for Data Protection full-disk encryption, since iOS has no standalone encryption toggle to query).
- **Android**: `securityProviderUpToDate` (`ProviderInstaller.installIfNeeded()`, the device's SSL/TLS implementation currency), `keystoreAttestationSecurityLevel` (`TrustedEnvironment`/`StrongBox`/`Software`/`Unavailable`, from a KeyStore attestation probe), `androidPlatformFamily` (`GMS`/`AOSP` — an AOSP device can never report Play Integrity, so root/RASP detection is its only integrity signal).
- **Android, via Google Play Integrity** (Classic API, verified server-side — `modules/playIntegrity/`, an admin-configured per-workspace Cloud Project Number + offline decryption key pair, see `docs/settings.md#google-play-integrity-api`): `playIntegrityVerdict` (best/highest device-integrity tier) and `playIntegrityAppRecognized` (confirms the exact, unmodified, Play-signed APK).
- **Both platforms, in-house RASP** (built to replace freeRASP, whose data-residency controls require its highest paid tier — a non-starter for a self-hosted SOAR that must keep this telemetry in its own pipeline): `deviceRootedOrJailbroken`, `deviceDebuggerAttached` (a live debugger/tracer attached to the agent's own process — Android's `TracerPid`/`Debug.isDebuggerConnected()`, iOS's `sysctl` `P_TRACED` flag per Apple's QA1361), and `deviceHookingFrameworkDetected` (Frida/Xposed/Substrate/Cycript-style runtime instrumentation — Android's Frida server/port + `/proc/self/maps` scan, iOS's dylib probe + `_dyld_image_count()` loaded-image scan).

All 9 of these are discoverable, friendly, type-aware Compliance Policy conditions (not just raw free-text `selfReportedAttribute` names) via `SELF_REPORTED_ATTRIBUTE_CATALOG` (`modules/compliance/complianceFields.ts`) — see §9.2. The mobile agent's Diagnostics drawer also carries **Force evaluate compliance** and **Force report to SOAR** actions, calling `POST /api/device-data/evaluate-now` and the same `POST /api/device-data/report` respectively, the same two on-demand actions the Windows/macOS agents' own tray/menu already had.

### 9.1 Custom Device Checks

`modules/compliance/customChecks.service.ts` (backed by the `CustomCheckDefinition` model) lets an admin define an arbitrary check scoped to a single platform. `GET /api/device-data/custom-checks?platform=windows|macos` (also device-report-secret/mTLS gated) is what each agent polls once per report cycle; results ride back in the same `POST /api/device-data/report` call under `customCheckResults`, keyed by the check's stable `key`. `complianceEvaluate.ts`'s `customCheckResult` condition type reads `device.selfReported.customCheckResults[key]` and treats a check that errored while running (as opposed to a legitimate negative result) the same as "missing."

Five checker types exist — process running, service/launchd-job running, a registry value or plist key/file existence, an installed app's version, or an unrestricted shell command — implemented independently by the Windows/macOS agent repos (`customchecks_windows.go` / `customchecks_macos.go`). **`ios`/`android` were removed from `CHECK_PLATFORMS` entirely** (`customChecks.schemas.ts`) after confirming the mobile agent never actually implements or reports any custom check at all — no method channel, no local probe, `device_report_client.dart` never sends a `customCheckResults` field. The only checker type ever offered for mobile (`appInstalled`) was consequently a dead, silently-never-matching option: it could be created in the UI, look completely valid, and simply never produce a result. Real installed-app data for iOS/Android already exists via the separate, working **App Lists** feature (`requiredAppList`/`disallowedAppList` conditions, sourced from Apple/Android MDM's own installed-apps API) — so this was a removal of a redundant, non-functional path, not a capability loss. `complianceFields.ts`'s `customCheckResult` field definition is now scoped `platforms: ["windows", "macos"]` so it no longer even appears as a selectable Policy Builder field on an apple/android-targeted policy.

### 9.2 Policy Builder discoverability for mobile telemetry

`getSelfReportedAttributeNames` (`modules/devices/deviceData.service.ts`) is purely observational — it returns whatever attribute names a real device has actually pushed so far, so a freshly onboarded workspace with no mobile device having reported yet saw an empty, unlabeled free-text suggestion box for all 9 mobile attributes above. `SELF_REPORTED_ATTRIBUTE_CATALOG` (`complianceFields.ts`) fixes this non-invasively: a static catalog of friendly label / value type (`boolean`/`enum`/`string`) / enum options / applicable platforms for each known attribute, merged with (not replacing) the real observed names via `getSelfReportedAttributeCatalog()`, exposed alongside the existing `items` array from `GET /api/compliance/self-reported-attribute-names`. `ConditionRow.vue`'s value editor renders a proper Yes/No select for a boolean attribute or an enum dropdown for one with fixed options, instead of a generic "Expected value…" text input — the underlying condition JSON shape (`{field: "selfReportedAttribute", value: {name, compareValue}}`) is byte-for-byte unchanged, so `complianceEvaluate.ts`'s `evaluateCondition` needed zero changes; this is purely a Policy Builder presentation-layer improvement. The same two new RASP attributes (`deviceDebuggerAttached`/`deviceHookingFrameworkDetected`) also got dedicated condition-builder functions and 12 new `critical`-severity Template Gallery entries (2 attributes × android/apple × ISO27001/ENS/NIS2), mirroring the existing `deviceRootedOrJailbrokenCondition()` pattern.

### 9.3 Distribution — zero-config download + Publish to Applivery

Both agent repos are private (their source has nothing tenant-specific in it, but the repos themselves aren't meant to be public), which originally meant offering a compiled binary from Settings required a GitHub Personal Access Token — something no actual customer has. `modules/settings/agentBuilds.service.ts`/`agentBuilds.controller.ts` solve this the same way this project already solves it for its own Docker images: each agent repo's own CI (`build.yml` / `build-pkg.yml`) POSTs its freshly-built binary straight into this backend after every push to `main` (`POST /api/internal/agent-builds/:platform`, gated by a single operator-held `AGENT_BUILD_INGEST_SECRET` shared-secret header — not a GitHub PAT, not per-workspace — verified by `middleware/agentBuildSecret.middleware.ts`, same fail-closed/constant-time-compare shape as `verifyTriggerSecret`). An optional `X-Agent-Arch` header (default `amd64` for windows, `arm64` for its second variant, `universal` for macos) identifies which of the Windows agent repo's two WiX-built MSIs (x64 and ARM64) this is. The binary lands in a rolling `AgentBuild` table, one row per `(platform, arch)` (Postgres `Bytes` column, sha256-tracked) and is then served with **zero authentication** from `GET /api/agent-downloads/:platform[?arch=]` — a customer's browser hits this directly from Settings, no token, no login, exactly like `docker pull` against a public GHCR image. `GET /api/agent-downloads` (no platform) lists every published variant at once, which is what Settings uses to render its three rows (Windows x64, Windows ARM64, macOS).

The same stored bytes back a second, admin-triggered flow per variant: `POST /api/settings/agent-downloads/publish/:platform/:arch` (dashboard-authenticated, `settings:manage`, run with the clicking admin's own live Applivery session) uploads the binary as an `mdmAsset` (`upload.applivery.io/mdm/assets` — the same multipart pattern `workflows/scriptAssetUpload.ts` already uses for script assets) and then creates or updates a real Applivery application from it, so the agent can be assigned to Policies like any other managed app. The asset's `name` is a clean, human-facing label ("Applivery SOAR Agent (Windows x64)") with no id in it; the exact build version instead rides in the asset's `description` as a `[build:<version>]` token, which a lookup by `subType`+`name`+that token checks *before* every upload — if this exact version is already up there, publish halts as a no-op (`alreadyPublished: true`) instead of creating a duplicate asset, which is what happened on a repeat click before this check existed. Windows and macOS diverge on the application step: Applivery's Windows enterprise-application endpoint accepts a settable `info.name`; the Apple/macOS endpoint has no equivalent field. Either way, `WorkspaceState.windowsAmd64AgentApplicationId`/`windowsArm64AgentApplicationId`/`macosAgentApplicationId` remember each variant's created application id per workspace, letting a republish update it in place instead of accumulating duplicates.

The original GitHub-token-proxied download path (`modules/settings/agentDownloads.service.ts`, proxying each repo's own GitHub Releases) is kept as a secondary, collapsed "Advanced" option in Settings — useful for a deployment that already had a token configured, or anyone who'd rather not rely on this app's own build mirror. The zero-config path now mirrors every build the Windows agent repo's CI produces (x64 and ARM64 MSIs, each its own `AgentBuild` row keyed by `(platform, arch)`) plus the single macOS universal `.pkg`.
